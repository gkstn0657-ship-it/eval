# 1006 실험: 청킹 방식 비교 (사전등록, 2026-10-06 작성, 측정 전)

## 목적

현재 파이프라인은 조(條) 단위 청킹을 쓰지만, 다른 분할 방식과 비교한 적이 없다. 같은 검색 파이프라인·같은 평가 세트에서 청킹 방식만 바꿔 조 단위 채택이 타당한지 확인한다.

## 가설

- H1: 조 단위(C0)는 고정 길이(C1)보다 nDCG@5가 높다.
- H2: 조 단위(C0)는 의미 단위(C2)보다 nDCG@5가 높다.
- H3: 항 단위(C3)는 조 단위(C0)와 차이가 없거나 높다. (Parent-Child 검색 단계의 효과)

## 고정 변수

| 항목 | 값 |
|---|---|
| 원천 데이터 | L2 최신판(정책 A), 292개 기관, 조문 19,298개 |
| 조문 텍스트 | L2P 처리(개정이력 접두어) 적용 텍스트를 모든 조건이 공유 |
| 검색 파이프라인 | `hybrid_prefilter` (기관 사전 필터 → bge-m3 dense + BM25 → RRF k=60 → bge-reranker-v2-m3, 후보 30) |
| 기관 정보 | 평가 세트의 `context_org`·질의 속 기관명 (기존 평가와 동일) |
| 답변 생성 | 하지 않음. 검색만 측정하며 API 크레딧을 쓰지 않는다 |

## 조건

| ID | 코퍼스 이름 | 생성 규칙 |
|---|---|---|
| C0 | `L2P_A` (기존) | 조 1개 = 청크 1개. 1,200자 초과 조문은 항 경계 분할, 정의 조항은 호 단위 분할, 조 제목 접두어 |
| C1 | `CH_FIX_A` | 기관별로 조문을 원래 순서대로 이어 붙인 뒤 1,200자 창, 겹침 200자로 분할. 조 경계 무시 |
| C2 | `CH_SEM_A` | 같은 이어 붙인 텍스트에 chat_rag의 `semantic_chunk` 적용 (jhgan/ko-sbert-nli, buffer 1, 거리 85 백분위 분할, 500자 초과 시 500자·겹침 50 고정 분할) |
| C3 | `CH_PARA_A` | 모든 조문을 항(①~⑮) 경계로 분할, 각 조각에 `제N조(제목)` 접두어. 항이 없는 조문은 조 전체 1개 |

C3은 "항 단위로 찾고 조 전체를 반환"하는 Parent-Child 구성의 검색 단계와 같다. 채점이 조문 단위라 반환 단위는 검색 지표에 영향을 주지 않으므로, 검색 실험에서는 C3로 Parent-Child를 대신한다. 반환 단위의 효과는 답변 생성 평가 과제로 남긴다.

## 채점 규칙

- 기존과 같이 조문 ID 단위로 채점한다. 같은 조문의 조각은 하나로 합친다.
- 조 경계를 넘는 청크(C1, C2)는 **글자 수가 가장 많은 조문**에 귀속한다. 이것이 주 지표다.
- 민감도 분석: 청크에 포함된 모든 조문을 등장 순서대로 펼쳐 채점한다(`--expand`). 이 방식은 큰 청크에 유리하므로 보조 지표로만 보고한다.
- Q9(정답 없음) 문항은 제외한다.

## 지표와 판정 기준

- 주 지표: nDCG@5. 보조: Recall@5, MRR.
- 비교: C1·C2·C3 각각을 C0와 쌍대 비교. 부트스트랩 2,000회, 95% 신뢰구간.
- 세트별 결과와 229문항 합산 결과를 모두 보고한다.
- **판정**: 합산에서 C0보다 유의하게 높고, 어느 세트에서도 유의하게 낮지 않은 조건이 있으면 그 방식으로 교체를 검토한다. 그런 조건이 없으면 C0를 유지한다.
- 함께 기록: 조건별 청크 수, 평균·최대 길이, 임베딩 계산 시간.

## 실행 절차

Python은 `E:\conda_envs\rag_gpu\python.exe`, 작업 위치는 `3_성능테스트/`.

1. **코퍼스 생성** (`build_chunk_variants.py`, 작성 완료)
   ```
   python build_chunk_variants.py        # corpora/CH_FIX_A, CH_SEM_A, CH_PARA_A.jsonl + chunk_variants_stats.json
   ```
   각 행 필드는 기존 코퍼스와 같다(`chunk_id, article_id, org, revision_date, is_latest, article_no, article_title, text`). C1·C2는 `article_ids`(포함 조문 전체, 등장 순서)를 추가한다.

2. **평가 스크립트 수정** (`run_eval.py`, 반영 완료)
   - `to_articles`에 `--expand` 옵션: 켜면 `article_ids`를 펼쳐 채점.
   - 쌍대 비교 목록에 `CH_* vs L2P_A (hybrid_prefilter)` 3쌍 추가.

3. **임베딩 사전 계산** (GPU fp16)
   ```
   python precache_embeddings.py CH_FIX_A CH_SEM_A CH_PARA_A
   ```

4. **평가 실행** (세트마다 1회, dev는 기본 골든셋이라 `--gold` 생략)
   ```
   python run_eval.py --corpora L2P_A,CH_FIX_A,CH_SEM_A,CH_PARA_A --pipelines hybrid_prefilter --tag chunk_dev
   python run_eval.py --corpora L2P_A,CH_FIX_A,CH_SEM_A,CH_PARA_A --pipelines hybrid_prefilter --gold ../1_데이터셋/06_eval/goldenset_employee.jsonl --tag chunk_employee
   python run_eval.py --corpora L2P_A,CH_FIX_A,CH_SEM_A,CH_PARA_A --pipelines hybrid_prefilter --gold ../1_데이터셋/06_eval/goldenset_kgs_faq.jsonl --tag chunk_kgs_faq
   python run_eval.py --corpora L2P_A,CH_FIX_A,CH_SEM_A,CH_PARA_A --pipelines hybrid_prefilter --gold ../1_데이터셋/06_eval/goldenset_matrix.jsonl --tag chunk_matrix
   ```
   민감도 분석은 같은 명령에 `--expand`와 `--tag chunk_<세트>_expand`.

5. **합산 분석**: `python chunk_pool.py` (펼침 채점은 `--expand`). `results_chunk_*`의 `per_query.json`을 모아 229문항 합산 부트스트랩.

6. **결과 문서**: `4_결과분석/청킹비교_결과.md`. 가설별 채택·기각, 세트별·합산 표, 실패 사례 3건 이상.

## 위험과 대응

- **GPU 메모리 3GB**: 임베딩은 사전 계산 단계에서만 GPU를 쓰고, 평가 중에는 재랭커만 GPU에 올린다(기존 방식).
- **의미 단위 분할 시간**: 문장마다 임베딩을 계산하므로 C2 생성이 가장 오래 걸린다. 1시간을 넘기면 기관 표본을 줄이지 않고 배치 크기만 조정한다.
- **조 경계 귀속 편향**: 주 지표(최다 글자 조문 귀속)는 C1·C2에 불리할 수 있다. 그래서 펼침 채점을 함께 보고하고, 두 방식의 결론이 다르면 결론을 유보한다.
- **사전등록 이후 변경**: 조건·채점·판정 기준을 바꾸면 이 문서에 날짜와 이유를 덧붙인다.
